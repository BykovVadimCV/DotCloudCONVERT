# Разбор «Конвертер E57 → 2D растровый план: как писать программу» (v1, 07.10.2026)

## 0. Коротко

1. **Идея реализуема**, основной путь выбран верно: свободное пространство по лучам от станций → растр →
   U-Net (топология) → размеры по точкам (refine). Чтение E57 — не риск, это проверено.
2. **Главные риски** — не там, где больше всего текста: проёмы, закрытые двери, стекло и то, что U-Net,
   обученный на чертежах, увидит растр другого вида. Под это и нужна синтетика.
3. **BlenderSynther как основа синтетики не годится**: это аддон для рендера RGB-картинок и масок
   для детекции объектов, к облакам точек отношения не имеет и в текущем виде не запускается.
   Синтезатор написан заново на NumPy + Open3D (пакет `simscan/` в этом репозитории).

## 1. Что я перепроверил сам

Окружение: Linux, Python 3.13.16, numpy 2.5.3, pye57 0.4.19, Open3D 0.20.0, OpenCV 5.0, scipy 1.18.

| Утверждение ТЗ | Результат |

| Чтение кусками `make_buffers` + `reader.read()` даёт те же точки, что `read_scan` | Подтверждено кодом из 5.1 на 4 сканах по 3,2–3,7 млн точек с повёрнутыми позами и недействительными точками: расхождение 0,0 |
| pye57 сам применяет позу, выкидывает ненулевой InvalidState | Подтверждено по исходнику `e57.py` и тестом `tests/test_e57.py` |

| RaycastingScene: ~3,7 млн лучей за ~1,3 с | Согласуется: сцена из 4 станций × 3,75 млн лучей + запись 14 млн точек в E57 + превью = 23 с на 4 ядрах |

Нашёл дополнительно:

- **pye57 пишет неверные `cartesianBounds`** при повороте позы: глобальный габарит считается поворотом
  только двух углов локального габарита. Конвертеру на `cartesianBounds` из таких файлов опираться нельзя.
- **Open3D на Linux требует системную `libEGL.so.1`** (`apt install libegl1`), иначе `import open3d` падает.
  Для Windows/PyCharm неактуально, для Colab, сервера и CI — актуально.
- **`RaycastingScene.compute_distance` в Open3D 0.20 ошибается до 4,5 мм** на длинных тонких треугольниках
  (плинтус 8 м × 7 см): точка, полученная рейкастом *этой же* сцены, «отстоит» от неё на 1,8 мм, аналитическое
  расстояние — 7·10⁻⁷ м. Для метрик точности уровня LOA30 этот вызов не использовать
  (в `simscan/scene.py` есть точная `surface_distance`).
- Минимальная дальность сканера (0,5–0,6 м) больше типичного отступа станции от стены — у ближней стены
  будут законные дыры. В синтетике это воспроизводится.

Не перепроверял: Windows-wheels, таблицу IoU из 5.5 (`freespace_poc.py` не приложен), внешние ссылки
(Zenodo, ISPRS, диапазоны LOA) — пометки ТЗ для них остаются в силе.

## 2. С чем согласен

1. **Плотностной срез = две грани с пустотой.** Это физика TLS: сканер видит поверхности, а не тела.
   На превью синтетики (`preview.png`) это видно сразу.
2. **Свободное пространство как основной растр** — правильный выбор, если в E57 есть станции.
3. **Ввод:** куски + квантование сразу, `ignore_missing_fields=True`, предупреждение при единичных позах.
4. **Пол и потолок** — только с условием расстояния между пиками; RANSAC пола — только по полосе у пика.
5. **Поворот применять к точкам, а не к растру.**
6. **Размеры брать по точкам (refine), маска — только топология.** Без этого LOA30 недостижим в принципе.
7. **Предупреждения вместо тихих исправлений**, фиксированный список кодов для гейта автоприёмки.
8. **Роли в синтетике:** лучи пускает Open3D, а не `bpy.ray_cast`; эталон — из планировки, а не из
   облака; запись через тот же pye57, что и чтение; сначала 2D-обучение; синтетика для старта,
   реальные объекты — для дообучения и отдельной валидации.
9. **Метрики в уровнях USIBD LOA** и сравнение с Cloud2BIM как базовой линией.

## 3. С чем не согласен или что уточнил бы

1. **BlenderSynther.** Это аддон Blender 2.91 для рендера RGB-кадров и масок по `pass_index`
   (случайные повороты объектов, фон-плоскость с текстурами, переключение света). Ничего из того, что ему
   приписывает раздел 9.1 (выдавливание стен, вырезы проёмов, створки, стекло, мебель, экспорт мешей
   с метками), в нём нет. Кроме того, он в текущем виде не работает:
   - `labeled_object = xyu` — NameError;
   - `BS_CameraContainer` нигде не определён, `BS_CollectionsManager` закомментирован, но используется;
   - `follow_path_constraint.target = …` — переменная не определена (создана `camera_container_follow_path_constr`);
   - `_compose_scene_render_changes` при фоне `custom` возвращает `None`, а `set_next_scene_render_state`
     по нему итерирует — TypeError на первом кадре;
   - в сообщении `FileNotFoundError` используется неопределённая `allowed_texture_extensions`.

   Переиспользовать стоит только идеи: «коллекция = класс» и `dataset_info.json`. **Blender для MVP
   не нужен вообще**: этаж — это параллелепипеды, их проще строить NumPy-кодом — без bpy, в фоне,
   параллельно, детерминированно по seed. Blender остаётся опцией для библиотеки мебели (импорт мешей)
   и для просмотра (`mesh.ply` открывается в нём, CloudCompare, MeshLab).

2. **Максимум дальности по корзине неустойчив к выбросам.** Один смешанный пиксель, отражение в зеркале или
   пылинка прорезает «щель» сквозь стену на всю длину луча. На синтетике видно, что хвосты смешанных
   пикселей у кромок дверей тянутся на метры. Вместо `max` — k-я по величине дальность в корзине или условие
   «не меньше N точек на этой дальности»; сравнить с 3D-вокселями (счётчики «попал / прошёл сквозь»).
   Проверять на синтетике с включёнными `mixed_pixels` и `mirrors` — для этого у эффектов отдельные флаги.

3. **2D-проекция луча считает свободной всю высоту вдоль проекции.** Для стен до потолка это верно, для
   низких перегородок, парапетов, барных стоек, стеклянных перегородок и фрамуг — нет. Улучшение: свободное
   пространство по полосам (учитывать только участки лучей внутри полосы low / plan / upper) → три канала.
   Это же даёт проёмы почти напрямую (п. 5).

4. **Закрытые двери в ТЗ не упомянуты**, а на реальных объектах их много. Для метода свободного пространства
   закрытое полотно — стена. Признаки: тонкий (≤ 6 см) участок, утопленный относительно граней стены,
   наличники, иная отражательная способность. В синтетике 20 % дверей закрыты (`p_closed_door`),
   в `gt.json` это поле `closed`.

5. **Логика проёмов 5.7 противоречит режиму свободного пространства.** Открытый дверной проём уже вырезан
   лучами из `wall_interior`, искать его «внутри тела стены» бесполезно. Логичнее работать с разрывами стены
   по полосам: разрыв в полосе plan, перекрытый стеной в upper, → проём; стена в low → окно, нет → дверь.
   Низ перемычки над дверью (2,0–2,1 м) лежит на нижней границе полосы upper (2,1 м) — порог на грани.

6. **Одноканальный plan.png для текущего U-Net — хороший эксперимент шага 4, но провал на проёмах
   ожидаем.** На чертежах окно — условное обозначение, а в растре свободного пространства окно — либо дыра
   наружу (стекло пропустило луч), либо стена (отразило). Такого сеть не видела. Я бы сразу закладывал
   многоканальный вход (свободное пространство + занятость low/plan/upper + доля занятых ячеек по высоте)
   и дообучение на синтетике.

7. **Наружные стены 0,4 м по умолчанию — можно лучше.** Откосы окон отсканированы, их глубина даёт
   толщину стены (с поправкой на положение рамы). 0,4 м — только для фасадов без окон.

8. **Пол и потолок.** В комнатах с мебелью пик столешниц (0,72–0,76 м) может обогнать закрытый мебелью пол,
   а расстояние «столешница — потолок» больше 1,8 м, так что условие distance его не отсеет. Надёжнее
   опираться на высоты станций: пол на 0,8–2,0 м ниже станции. Подвесные потолки в части помещений дают
   несколько пиков потолка — в синтетике это есть (`p_suspended_ceiling`).

9. **Номер скана на точку после квантования (5.1) теряется** при слиянии вокселей из разных сканов.
   Для свободного пространства точки хранить вообще не нужно: оно считается потоково по каждому скану
   (максимум или квантиль дальности по корзине) до слияния. На объектах в сотни миллионов точек это решает
   вопрос памяти.

10. **Сроки раздела 10 оптимистичны.** «refine + LOA + vertical + openings» за 2 дня — проёмы самая трудная
    часть; я бы закладывал на них неделю с синтетическими тестами.

11. **Мелочь:** на pyquaternion лучше не опираться — кватернион → матрица это 10 строк
    (`simscan/transform.py`, тест против pyquaternion есть).

## 6. datasetgen и BLK360 (вторая итерация)

### Что выяснилось про datasetgen

1. **Всё в пикселях, физического масштаба нет.** Контур — 44–76 % холста, толщина стены — независимо
   3–100 px × super_sampling. Отношение «стена / комната» гуляет в разы — для 2D-обучения это
   аугментация, для 3D-сцены толщины нужно разыгрывать заново в метрах.
2. **Двери и окна есть только в растре** (и в YOLO-разметке), в структурах данных их нет. В JSON
   метаданных нет даже стен — по нему план не восстановить. Предложение: добавить в
   `MetadataExporter` стены и проёмы (ось, толщина, тип, положение) — тогда адаптер сможет брать
   проёмы оттуда же, а план и скан будут описывать одну квартиру.
3. **Стратегия `bsp` сломана:** комнаты покрывают в среднем 32 % контура (медиана пропуска 68 % по
   30 планам), стены — обрывки; фактически это пустая коробка. **`voronoi`:** комнаты перекрываются
   (медиана 47 % площади посчитано дважды), внутренних стен нет вовсе. **`courtyard`:** комнаты
   не разделены стенами. В 2D это просто «странные» картинки, в адаптере `bsp` и `voronoi` выключены.
4. **Инициализация маски работает случайно правильно:**
   `to_pixel_value(to_pixel_value(FOOTPRINT))` = `to_pixel_value(255)` = 0, то есть холст — фон,
   а не «footprint», как написано в комментарии. Это и даёт 4 класса, которые ждёт
   `unet_inference.py` (`NUM_CLASSES = 4`). Если кто-то «исправит» двойной вызов, маски зальются
   значением 255 (класс 4) и перестанут совпадать с моделью. Лучше заменить на явный 0 и поправить
   комментарий.
5. **Двери ставятся на каждую внутреннюю стену с вероятностью 0,75 в случайное место**, без учёта
   смежности комнат: часть комнат без входа, часть дверей у Т-образных стыков. Для 2D терпимо,
   адаптер ставит двери сам по остовному дереву смежности.
6. **id комнат** берутся из глобального `random` (`default_factory=random.randint`), а не из
   сидированного генератора — в JSON метаданных они разные от запуска к запуску при одном seed.
7. **Класс «дверь» в маске включает дугу открывания.** В облаке точек дуги нет, есть полотно —
   в `unet_mask.png` simscan дверь = проём + полотно, без дуги. При смешивании чертёжной
   и сканерной синтетики в одном обучении это стоит помнить.

### Что из этого следует для конвертера

- U-Net ReFloor: 4 класса, RGB-вход, `A.Resize(1024)`, а размер входа подбирается так, чтобы
  основная стена была ~30 px (`core/scale_norm.py`). Значит, `plan.png` конвертера должен рисоваться
  в том же кадре: шаг пикселя = толщина наружной стены / 30. `gt/unet_mask.png` simscan уже в этом
  кадре (`gt.json → unet.frame`), растр скана для обучающих пар должен строиться в нём же.

### BLK360

По спецификациям Leica: G1 — 0,6–60 м, поле зрения 300° по вертикали, шаг 5/10/20 мм на 10 м,
точность дальности 4 мм на 10 м; G2 — 0,5–45 м, 270° по вертикали, 6/12/25/50 мм на 10 м,
3D-точка 4 мм на 10 м. Для конвертера важно:

- **G2 не видит конус 45° под собой:** на полу у каждой станции дыра радиусом примерно
  в высоту станции (1,3–1,7 м). Для пола по гистограмме это не страшно, для свободного пространства
  тоже (лучи к полу у станции ничего не добавляют), но плотностной срез у пола будет дырявым.
- **Шум у BLK360 заметно больше стартового пресета simscan** (0,5–2,5 мм): 4 мм на 10 м. Для отступа
  margin в методе свободного пространства (раздел 5.5 ТЗ: 2 см на синтетике с шумом 2 мм) это
  значит подбирать заново: ориентир — 3σ на типичной дальности 3–6 м, т.е. 6–9 мм для G1.
- Регистрация у BLK-линейки обычно визуально-инерциальная плюс облако-к-облаку в Register 360,
  ошибки станций в пресете взяты 2–6 мм — НЕ ПРОВЕРЕНО.
- Как именно Register 360 экспортирует E57 (скан на станцию с позой или одно облако, сферические
  или декартовы, есть ли сетка строк/столбцов) — НЕ ПРОВЕРЕНО. Это решает, работает ли метод
  свободного пространства вообще; нужен один реальный файл.

## 7. Движок планировок (третья итерация)

Что смотрел и почему выбрал так:

| Вариант | Лицензия | Что даёт | Решение |
|---|---|---|---|
| ProcTHOR (allenai/procthor) | Apache-2.0 | Рост комнат на сетке (Lopes 2010), зоны, двери по иерархии; чистый Python | **Взят за основу** |
| Infinigen Indoors (princeton-vl/infinigen) | BSD-3 | Граф комнат + разбиение контура + отжиг по ограничениям; качество выше | Завязан на Blender, gin и свой язык ограничений - перенос долгий; ориентир на будущее |
| HouseGAN++, Graph2Plan, HouseDiffusion | код открыт | Обучены на RPLAN | Данные RPLAN - только некоммерческие; для фирмы не годится |
| datasetgen | свой | Разнообразие картинок для 2D | Оставлен вторым источником (`layout.source: datasetgen`) |
| Swiss Dwellings (Archilyse, ~42 тыс. квартир, стены/двери/окна в метрах) | НЕ ПРОВЕРЕНА (zenodo недоступен из этой среды) | Реальные планы, не генератор | Лучший кандидат на реальную валидацию, если лицензия позволит коммерческое использование |

Почему ProcTHOR, а не Infinigen: для задачи «обучающие пары скан -> план» нужны тысячи
правдоподобных квартир за минуты, без Blender, с метками и в метрах; ProcTHOR переносится
целиком (~300 строк), Infinigen - только переписыванием.

Что добавлено поверх ProcTHOR, потому что ProcTHOR генерирует отдельные дома, а не квартиры:
фасады и межквартирные стены, вход с лестничной клетки, семена жилых комнат по долям фасада,
санузлы в глубине корпуса, лоджии (открытые и остеклённые) с балконным блоком, несущая стена,
проверки формы (не больше 6 углов, без узких отростков, минимальные ширины, площади)
и достижимости, перебор нарезок каждой зоны.

Состояние: студии, 1- и 2-комнатные строятся стабильно (почти все попытки за 1-3 с);
3- и 4-комнатные - редко, входная зона сдавливается большими комнатами. Следующий шаг для
них - разбиение верхнего уровня прямоугольниками (squarified treemap, Marson & Musse 2010)
вместо роста, а рост оставить внутри зон.

## 8. Реалистичность без Blender (A и B)

Почему не Blender: аддоны LiDAR для Blender тоже трассируют лучи (BlAInder - `BVHTree.ray_cast`
по одному лучу из Python, нормальный шум, Френель для стекла, GPL-3), то есть по физике сканера
не лучше Open3D. Blender даёт только удобство моделирования и библиотеки моделей - это закрыто
процедурной мебелью и загрузкой внешних моделей (`interior.asset_dir`).

Что важно для нашей задачи (вход сети - 2D-растр свободного пространства и срезов): не форма
спинки дивана, а где лучи проходят и где нет, и как ведут себя кромки и неровные стены.

Сделано:
- A: мебель из частей, шторы и тюль, коробки и наличники дверей, стояки, радиаторы, растения,
  светильники, декор на стенах; неровность, завал, отклонение углов, фактические толщины;
  загрузка внешних моделей.
- B: модель пятна луча с подлучами и выбором эха по энергии (смешанные пиксели появляются
  физически, только при близких поверхностях), шум от угла падения и растяжения пятна,
  пропуски по энергии с учётом частичного пятна, пропускание тюля.

Цифры на сцене BLK360 G2 (2-комнатная, 6 станций): +25-75 % времени на сцену (22 -> 27-38 с,
с отладкой), кромки - 1-7 % лучей, смешанные эхо - 0,4-5 % точек (зависит от станции),
неровность стены 0,3-1,4 мм СКО, с шумом 1,2-1,8 мм.

Не проверено и требует реального скана VESO: расходимость луча BLK360, разделение эхо,
уровень шума от угла, доля пропусков; модель пропусков, обученная на реальных данных (слой C).

## 9. Беспорядок, реальные сканы, обучающая пара (пятая итерация)

**Беспорядок.** Ровные параллелепипеды не дают «куртку на коробке». Добавлены мягкие сетки
(`furniture.py`): ткань на опоре (лежит на верхней грани, свисает за краями почти вертикально,
на полу ложится вбок, складки - гладкий шум), одежда на крючке (уже у ворота, шире книзу,
объём от стены), неровные кучи (сумки, бельё), стопки коробок со сдвигом и поворотом,
доски у стены под 70-82°. Уровень беспорядка на сцену `interior.mess` (по умолчанию 0..1)
масштабирует вероятности и количества. Для плана это важно тем, что такие вещи меняют
свободное пространство у стен и дают «стену» там, где её нет.

**Реальные сканы.** Из открытых наборов с подходящей для фирмы лицензией и прямой
загрузкой нашёлся Google Scanned Objects (1033 предмета, CC BY-SA 4.0; бакет Kubric
доступен и отсюда). Мебели в нём нет - это мелкие бытовые вещи; они ставятся в натуральную
величину (обувь, вещи на столах и полках, сумки и игрушки на полу). Мебель - Poly Haven
(CC0) и Objaverse (фильтр по лицензии): загрузчики написаны, в этой среде сайты закрыты,
нужна проверка у вас. 3D-FUTURE, ScanNet, Matterport3D - только некоммерческие, не берём.

**Обучающая пара.** Вход - псевдочертёж по свободному пространству (`rasterize.py`), цель -
маска U-Net. Найденные по ходу ловушки:
- за остеклением лоджии бывает земля на уровне пола - свободное пространство «вытекало»
  наружу. Пол теперь ограничен потолком + 0,6 м (снаружи потолка нет);
- неотсканированные комнаты: в эталоне они есть, во входе пусто. Без маски сеть учили бы
  выдумывать стены - добавлена `input/valid.png` для функции потерь;
- базовая линия без сети на 6 сценах - IoU стен 0,27-0,49 (полнота 0,5-0,96). Толщина кольца
  наружных стен на неё почти не влияет (0,15-0,4 м: ±0,05) - мешают шкафы до потолка, тени
  и неотсканированное.

Открыто: проверить на реальном скане VESO, что псевдочертёж из настоящего BLK360 похож на
синтетический (особенно пол и потолок - пики гистограммы и подвесные потолки).
